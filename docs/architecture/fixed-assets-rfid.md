# Fixed Asset and RFID core

`assets` is the permanent operational identity. Its allocator atomically increments one row per institute; department, room, custodian, and EPC never form part of `asset_number`. Capital and controlled classification is independent of accounting capitalization. Procurement links are optional (including legacy recovery) and preserve PR → item → PO → line → GR → line provenance without duplicating Item Master or Stock Item identity.

Physical `asset_locations` are a separate hierarchy from organization units. Responsible department answers *who owns responsibility*; current location answers *where*. Only receipt in the canonical movement state machine updates current location, transactionally with audit. RFID can corroborate but never authorizes a movement or changes location/custody.

## Custody decision

Existing `custody_records` are administrative issue documents: they can represent a quantity, target a person/department/location, and carry user/HOD approval history. They are not an item-level asset register. Migration 017 adds only a nullable `asset_id` bridge so that existing custody remains the single administrative custody history. No competing asset-custody table is introduced. RFID processing never writes custody.

## RFID boundaries

Tags are replaceable children of assets; active EPC and primary-UHF invariants are database enforced and prior tags remain historical. Readers, antennas, portals and their mappings are vendor-neutral. Integration secrets are generated with 256 bits of entropy and verified with HMAC-SHA-256 using the required `RFID_CREDENTIAL_PEPPER` (at least 32 characters); the pepper is configuration, never a database value. Plaintext is returned only by create/rotate, comparisons are constant-time, and disabled or incorrectly scoped clients fail closed. Normal human JWTs cannot authenticate ingestion, and service credentials never enter the human route stack. A vendor adapter must convert SDK payloads into normalized observations.

Raw reads are immutable technical observations, accepted in batches of up to 500 with explicit-offset timestamps and a 16 KiB raw-payload ceiling, preserved even when an EPC is unknown, and deduplicated only by integration client plus supplied external event ID. They are not individually audited. The retryable processor claims bounded work with `SKIP LOCKED`, commits each logical read independently, and aggregates short-window reads into business events. Ordered SIDE_A/APPROACH to SIDE_B/DEPARTURE evidence produces deterministic entering/exiting direction and confidence; insufficient or unoriented evidence stays `UNKNOWN`. Exactly one compatible approved/in-transit movement makes a portal event authorized, none makes it unauthorized, and multiple matches remain explicitly ambiguous. Unknown and unauthorized logical events each create at most one exception. None of these outcomes performs automatic receipt, location, responsibility, or custody updates.

Portal orientation is deliberately probabilistic evidence rather than physical truth. One enabled antenna may map to at most one enabled portal. SIDE_A/APPROACH is the portal's configured `from_location_id` side and SIDE_B/DEPARTURE is its `to_location_id` side; deployments must validate and tune this convention against their installation.

## Migration governance

Migration 017 is a deployed, immutable manual migration. It preflights canonical dependencies and recognizes only three states: no core objects (install), a complete catalog-compatible state (successful no-op), or any partial/drifted state (exception `SQL_017_PARTIAL_OR_DRIFTED_SCHEMA`). Later schema requirements must not be added to its compatibility check: migration 026 owns the forward-only `rfid_portal_enable_scope` index, while migration 027 upgrades the two SQL 018 guards and adds reader/antenna mutation guards. Each later migration validates its predecessor and safely no-ops only when its own complete shape is present. The allocator uses PostgreSQL's atomic `INSERT … ON CONFLICT DO UPDATE … RETURNING` per institute, so issued values are never recycled. The default prefix is `WICI-A`; changing a stored institute allocator prefix is a governed administrative decision and never rewrites an existing asset number.

## Physical inventory and reconciliation

Physical inventory is an **observation and reconciliation** domain, not a second asset register. `assets`, `asset_locations`, `asset_movements`, `custody_records`, and `asset_tags` remain authoritative. Inventory QR, manual, and RFID observations never update current location, organizational responsibility, custody, movement state, condition, or operational status. RFID reads and business events are referenced as evidence rather than copied into another RFID subsystem.

A session is institute-scoped and moves forward through `DRAFT → OPEN → COUNTING → REVIEW → COMPLETED`; it can be cancelled, with a reason, before completion. Entering `COUNTING` transactionally freezes active assets selected by location (optionally recursive descendants), responsible department, or full institute into `asset_inventory_expected_assets`. The snapshot stores stable IDs and human-readable identity, location, department, section, custodian, condition, status, category, and active EPC values. A database trigger rejects snapshot updates and deletes. Later asset, custody, location, or tag changes therefore cannot rewrite count history.

All input methods call one normalized observation service. QR and manual input resolve the permanent `asset_number`; RFID resolves an active `asset_tags.epc` and may retain `rfid_read_events`/`rfid_business_events` references and raw metadata. Institute identity comes only from authenticated context. Same-institute assets outside the snapshot become `UNEXPECTED`; foreign and unknown identities fail closed. A deterministic session/method/asset/location key preserves one useful normalized observation while raw RFID history remains in the canonical read tables.

Reconciliation runs only when counting closes into `REVIEW`. Until then, absence means *not observed yet*, never missing. Review compares the immutable expectation with the latest applicable observation and can preserve multiple findings: `VERIFIED`, `MISSING`, `UNEXPECTED`, `WRONG_LOCATION`, `RESPONSIBILITY_MISMATCH`, `CUSTODY_MISMATCH`, `IDENTIFICATION_CONFLICT`, `CONDITION_MISMATCH`, `STATUS_MISMATCH`, and `REQUIRES_INVESTIGATION`. Unregistered discoveries have an `UNREGISTERED` finding. Findings remain visible after acknowledgement, resolution, or dismissal; append-only resolution rows retain their history.

Expected-at-start, observed-during-count, and current-authoritative state are displayed separately. Reconciliation checks received canonical movement history after the snapshot and marks explanatory context as `explained_by_movement`; it never alters the snapshot or assumes the discrepancy was unauthorized. Critical open or acknowledged findings block completion.

Legacy physical discoveries capture only observed description, maker/model/serial, physical location, known department, condition, notes, and evidence metadata. They do not create assets. `Register Legacy Asset` hands off to the canonical fixed-asset creation service with `creation_source = LEGACY_RECOVERY` and retains the discovery-to-asset provenance; missing acquisition, supplier, PO/GR, custody, and historical deployment facts are not invented.

Corrections are explicit canonical workflow handoffs. Wrong location offers the existing movement request service; custody opens the existing custody workflow; legacy discovery uses canonical asset creation; responsibility, condition, and status remain under governed asset review/update. Each inventory mutation and each invoked canonical transaction keeps its own audit trail. The narrow server-side capabilities are `fixed-assets.inventory.view`, `.create`, `.count`, `.review`, and `.resolve`; no role names are embedded.

Migration 030 is manual and forward-only. It owns the session allocator, sessions, immutable expected snapshot, normalized observations, discoveries, findings, and append-only resolution history. It preflights SQL 017 dependencies, no-ops only for a complete compatible installation, and rejects partial/drifted states. Repository contents label migrations 018–030 pending, so actual deployment status must be confirmed by the operator before manual execution.

Vendor SDKs, trigger integrations, fixed-reader automated inventory, proximity locating, and automatic relocation/custody/missing writeback remain intentionally outside this boundary.
